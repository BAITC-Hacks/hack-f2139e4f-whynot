# Контракт API для frontend

Базовый URL: `http://127.0.0.1:8000/api/v1`. Интерактивная схема: `/docs`, JSON: `/openapi.json`.
JSON-поля — `snake_case`. Запросы с телом передаются как `application/json`, кроме
`POST /ai/transcribe`: он принимает `multipart/form-data` с полем `file`.

## Аккаунты

Используйте `/auth/register`, `/auth/login`, `/auth/me`, `/auth/logout` и cookie-сессии
с `credentials: include`. Изменяющие запросы требуют разрешённый `Origin`.
Восстановление пароля, профиль бизнеса, голосовой ввод и история описаны в
[дополнении к контракту](accounts-and-history.md). `X-Actor-ID` не авторизует реальный аккаунт.

## Пользователь демо

Только при явном `DEMO_MODE=true`, `GET /demo/actors` отдаёт синтетических пользователей.
Для тестовых операций без зарегистрированного аккаунта:

```http
X-Actor-ID: business-1
```

`business-1` — бизнес; `student-1` … `student-5` — представители команд.
Это переключатель демо-роли, не настоящая аутентификация.

## Маршруты

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `POST /tasks` | Бизнес | Создать черновик, 201 |
| `GET /tasks/mine` | Бизнес | Собственные черновики и опубликованные задачи |
| `GET /tasks/{id}` | Владелец | Текущая редактируемая карточка и рейтинг |
| `POST /tasks/{id}/assist` | Владелец | Вопросы и предлагаемая карточка без сохранения |
| `PUT /tasks/{id}/card` | Владелец | Заменить текущую карточку |
| `POST /tasks/{id}/confirm` | Владелец | Подтвердить текущую редакцию |
| `POST /tasks/{id}/publish` | Владелец | Опубликовать подтверждённую редакцию |
| `GET /catalog` | Все | Снимки опубликованных карточек по рейтингу |
| `GET /catalog/{id}` | Все | Опубликованный снимок одной карточки |
| `GET /teams` | Все | Профили и баллы команд |
| `GET /teams/me` | Студент | Своя команда |
| `PUT /teams/me` | Студент | Создать или обновить свою команду |
| `POST /tasks/{id}/proposals` | Студент с командой | Отклик, 201 |
| `GET /tasks/{id}/proposals` | Владелец задачи | Список откликов для сравнения |
| `GET /proposals/mine` | Студент с командой | Свои отклики и решения |
| `POST /proposals/{id}/decision` | Владелец задачи | Принять или отклонить |
| `POST /proposals/{id}/milestones` | Владелец задачи | Подтвердить результат и начислить баллы |
| `GET /proposals/{id}/milestones` | Владелец задачи | Подтверждённые этапы |
| `GET /ai/contract` | Все | Промпт и схема AI для демонстрации |

## Сквозной сценарий

Создать задачу от бизнеса:

```json
{"raw_description":"Хотим прогнозировать остатки магазина","topic":"retail"}
```

В ответе есть `id`, `revision`, `card`, `rating`. Затем `POST /tasks/{id}/assist`:

```json
{
  "answers":{"data":"CSV продаж за 6 месяцев","users":"Закупщик магазина"},
  "previous_questions":[{"field":"data","question":"Какие данные о продажах доступны?"}]
}
```

`answers` и `previous_questions` необязательны; первый запрос может содержать `{}`.
История содержит последние 40 вопросов текущей задачи и помогает модели выбирать новые
уточнения. Backend передаёт модели описание, актуальную карточку с ответами, категорию,
критерии готовности с весами и историю. Это также позволяет уточнять расплывчатые
заполненные поля, а не только пустые. История не сохраняется на сервере.
Значение каждого поля в `answers` полностью заменяет его в предлагаемой карточке;
frontend объединяет прежние сведения с новыми дополнениями перед запросом.
Ответ содержит `provider`,
`fallback_reason`, `based_on_revision`, `suggested_card`, `questions` (минимум 3)
и `missing_fields`. Каждый вопрос: `{"field":"constraints","question":"..."}`.
Человек редактирует `suggested_card`, затем frontend отправляет `PUT /tasks/{id}/card`:

```json
{
  "expected_revision": 1,
  "card": {
    "title": "Прогноз остатков",
    "topic": "retail",
    "context": "Остатки ежедневно проверяют вручную",
    "need": "Сократить ручную работу закупщика",
    "users": "Закупщик магазина",
    "data": "CSV продаж и остатков за 6 месяцев",
    "constraints": "Две недели, Python, тестовые данные",
    "expected_result": "Прототип прогноза и инструкция",
    "success_criteria": "Ошибка меньше 15% на отложенных данных",
    "contact": "demo@example.com",
    "interaction_format": "Еженедельный созвон, обратная связь за два дня"
  }
}
```

Это полная замена: пропущенные поля станут пустыми. Отправляйте всю редактируемую карточку.
Не отправляйте `score`, `confirmed_fields` или `owner_id` — сервер определяет их сам.

Для `/confirm` и затем `/publish` используйте актуальную `revision` из ответа:

```json
{"expected_revision":2}
```

Сначала показывайте человеку карточку для подтверждения; `/confirm` вызывается только
по его действию. До подтверждения заполненность доступна в `rating.preview_score`,
а начисленные баллы — в `rating.score`. Каждый элемент `rating.breakdown` содержит
`points`, `max_points`, `missing_fields`, `unconfirmed_fields`, `suggestion`.

Каталог: `GET /catalog?topic=retail&readiness=ready&limit=20&offset=0`.
Ответ: `{"items":[...],"total":5,"limit":20,"offset":0}`.
Значения readiness: `draft`, `working`, `ready`, `priority`; каждый фильтр необязателен.
Снимок каталога не содержит приватный исходный текст или неподтверждённые правки.

От студента создайте команду через `PUT /teams/me`:

```json
{"name":"WhyNot","interests":["retail"],"skills":["ML"],"technologies":["Python"]}
```

Затем `POST /tasks/{id}/proposals`:

```json
{
  "idea":"Прогнозировать спрос по истории продаж",
  "plan":"Анализ данных, базовая модель, прототип и проверка",
  "timeline":"Две недели",
  "prototype_url":"https://example.com/demo"
}
```

Ссылка необязательна; если есть, допускаются только HTTP/HTTPS. Любая команда может
откликнуться на любую опубликованную задачу, независимо от рейтинга и других откликов.
ID команды берётся из текущего пользователя. `team_id` в ответе можно сопоставить с `/teams`.

От бизнеса `POST /proposals/{id}/decision`:

```json
{"decision":"accepted","note":"Готовы начать с прототипа"}
```

Для отказа — `rejected`. Система не выбирает команду автоматически. Другие отклики
остаются `pending`; бизнес может принять несколько предложений или отклонить все.
Повтор того же решения безопасен, изменение окончательного решения возвращает 409.

После проверки результата бизнес вызывает `POST /proposals/{id}/milestones`:

```json
{"code":"prototype","evidence":"Проверен прототип на согласованных тестовых примерах"}
```

Баллы: `prototype` 20, `pilot` 30, `delivery` 50. Повтор идентичного запроса не удваивает
баллы. Студент видит свою сумму через `/teams/me`.

## Ошибки

```json
{"error":{"code":"STALE_REVISION","message":"Карточка изменилась. Загрузите актуальную версию."}}
```

- `401 LOGIN_REQUIRED`: войдите в аккаунт или обновите истёкшую сессию.
- `403 BUSINESS_REQUIRED / STUDENT_REQUIRED`: не та роль.
- `404 TASK_NOT_FOUND / PROPOSAL_NOT_FOUND`: объект отсутствует или недоступен пользователю.
- `409 STALE_REVISION`: заново загрузить карточку и дать пользователю согласовать правки.
- `409 CONFIRMATION_REQUIRED`: сначала подтвердить текущую редакцию.
- `409 TEAM_REQUIRED`: создать профиль команды.
- `409 DECISION_FINAL / TEAM_NOT_SELECTED / MILESTONE_EXISTS`: недопустимый переход.
- `422 VALIDATION_ERROR / CARD_LABELS_REQUIRED`: исправить поля запроса.
- `429 RATE_LIMITED`: превышен лимит запросов.
- `503 AI_NOT_CONFIGURED / TRANSCRIPTION_FAILED`: голосовой ввод не настроен или недоступен.

Неизвестные поля, пустой обязательный текст, слишком длинные строки и некорректные URL
проверяются сервером. При сбое AI `/assist` отдаёт 200 с локальной заглушкой и объяснением.
