# Передача задачи frontend-разработчику

Backend находится в ветке `backend`. Frontend разрабатывается в отдельной ветке `frontend`
и каталоге `frontend/`. Чтобы иметь API и тестовые данные локально, новую ветку frontend
нужно создать от актуальной `origin/backend`.

## Подготовка ветки

Команды выполняются в локальной копии репозитория frontend-разработчика:

```sh
git status --short
git fetch origin
git switch -c frontend --no-track origin/backend
```

Команда создания применяется, только если ветка `frontend` ещё не существует.
`--no-track` оставляет новую ветку без привязки к `origin/backend`, чтобы случайный push
не отправил frontend-работу в backend.

Если `origin/frontend` уже существует, а локальной ветки нет:

```sh
git switch --track origin/frontend
git merge origin/backend
```

Если локальная `frontend` уже существует, переключитесь на неё, получите её удалённые
изменения, если они есть, и объедините с `origin/backend`. Сохраните незакоммиченные
изменения до переключения. Не пересоздавайте существующую ветку и не применяйте force push.

Backend запускается на машине frontend-разработчика по [README](../README.md).
Адрес `127.0.0.1` относится к собственному компьютеру, не к компьютеру тиммейта.
Демо-данные создаются командой `python -m app.seed` из `backend/` с Python из venv.

## Если GitHub-репозиторий архивирован

Архивированный репозиторий не принимает push. В этом случае backend можно передать
файлом `ai-sana-backend.bundle`: он содержит ветку `backend` вместе с историей Git.
Получатель сохраняет файл и создаёт из него новую локальную копию:

```sh
git clone -b backend ai-sana-backend.bundle ai-sana
cd ai-sana
git switch -c frontend --no-track backend
```

После этого доступны все исходники, инструкции и возможность делать коммиты в `frontend`.
В этой копии `origin` указывает на bundle-файл. Когда команда получит рабочий GitHub-репозиторий,
замените URL `origin` его адресом, выполните fetch, проверьте удалённую историю и отправьте
ветки обычным push без force. Если репозиторий назначения новый и пустой, достаточно:

```sh
git remote set-url origin https://github.com/OWNER/WORKING-REPOSITORY.git
git push -u origin backend
git push -u origin frontend
```

Замените пример URL реальным адресом. Для исходного репозитория требуется снятие архивации
владельцем или администратором. Чтобы пересоздать файл передачи после новых backend-коммитов:

```sh
git bundle create ai-sana-backend.bundle refs/heads/backend
git bundle verify ai-sana-backend.bundle
```

## Задача frontend

Если другой стек ещё не согласован, используйте React + TypeScript + Vite в `frontend/`.
Интерфейс на русском. Контракт уже реализован: [API](api.md), [архитектура](architecture.md).
После запуска backend также доступны `/docs` и `/openapi.json`.

Нужны следующие экраны:

1. Переключатель демо-пользователя: бизнес или одна из студенческих команд, данные из
   `GET /api/v1/demo/actors`. Выбранный ID отправляется в `X-Actor-ID`.
2. Кабинет бизнеса: список своих задач, создание из свободного описания и темы.
3. Конструктор: AI-вопросы, ответы и редактируемая карточка; рейтинг с расшифровкой,
   подсказками о недостающих полях и отдельными действиями подтверждения и публикации.
4. Общий каталог: сортировка сервера по баллам, фильтры по теме и готовности, пагинация,
   карточка опубликованной задачи. Низкий рейтинг не блокирует просмотр или отклик.
5. Кабинет команды: профиль, форма отклика (идея, план, срок, необязательная ссылка),
   свои отклики и их статусы, баллы за подтверждённые результаты.
6. Отклики на задачу бизнеса: данные команд, сравнение предложений, ручные кнопки
   принятия и отказа. Можно принять несколько предложений.
7. Для принятого отклика — подтверждение этапа бизнесом с описанием результата.

## Важные правила интеграции

- API-клиент получает базовый URL из `VITE_API_BASE_URL`; пример:
  `http://127.0.0.1:8000/api/v1`. Конфигурационный пример хранится в `frontend/.env.example`.
- Vite запускается на `http://localhost:5173` или `http://127.0.0.1:5173`: эти origins
  уже разрешены backend. При занятом порте лучше сообщить об этом, чем незаметно сменить порт.
- Сохраняйте `snake_case` из API; не выдумывайте новые маршруты или поля запроса.
- `PUT /tasks/{id}/card` полностью заменяет карточку. Передавайте все поля и актуальную
  `expected_revision`, затем сохраняйте новую `revision` из ответа.
- `/assist` возвращает предложение, не сохраняет его. Покажите его пользователю и
  применяйте явно. При изменении карточки учитывайте `based_on_revision`, чтобы старый
  AI-ответ не затёр новые пользовательские правки.
- Для следующего раунда `/assist` передавайте накопленные сведения в `answers` и
  последние 40 вопросов текущей задачи в `previous_questions`. Ответ дополняет известный
  текст поля; название и тема заменяются. Очищайте ввод только после успешного запроса.
  Поля `answers` — полные новые значения, поэтому объединяйте прежний текст с ответом
  перед отправкой. Историю не переносите между задачами.
- Рейтинг рассчитывает сервер. `score` — подтверждённые баллы, `preview_score` — возможные
  баллы после подтверждения; показывайте их различие. Не отправляйте вычисленный клиентом рейтинг.
- Подтверждение — осознанное действие бизнеса после просмотра карточки. Затем вызывается
  публикация. После редактирования опубликованная версия остаётся прежней до новой публикации.
- `status=draft` означает приватный черновик, а `readiness=draft` — низкую готовность;
  опубликованная задача тоже может иметь такую готовность.
- Авторизация демонстрационная. При смене пользователя очищайте данные предыдущего
  кабинета и выполняйте новые запросы. Не показывайте чужую карточку из старого кэша.
- Ошибки имеют формат `{"error":{"code":"...","message":"..."}}`. При 409 устаревшей
  версии предложите загрузить актуальную карточку, сохранив несохранённый текст для сравнения.
- При `provider=stub` честно показывайте режим заглушки; при наличии `fallback_reason`
  показывайте причину. Нельзя выдавать заглушку за работающую модель.
- Нужны состояния загрузки, пустых списков, сетевой ошибки и блокировка повторного
  нажатия кнопки во время отправки. Основной сценарий должен использовать настоящий API.

## Приёмка

1. Запустить backend с демо-данными и frontend.
2. Создать слабое описание от бизнеса, получить минимум три вопроса, заполнить карточку.
3. Показать рост рейтинга после ручного подтверждения, опубликовать задачу.
4. Переключиться на студента, найти задачу в каталоге и отправить отклик.
5. Вернуться к бизнесу, вручную принять или отклонить предложение.
6. Для принятого предложения подтвердить результат этапа и увидеть баллы команды.
7. Перезагрузить страницу и проверить сохранение данных через API.
8. Выполнить сборку frontend, проверку типов и настроенные проверки проекта.

Добавьте `frontend/README.md` с установкой, запуском, переменными окружения и проверками.
Затем закоммитьте только файлы своей задачи и отправьте ветку:

```sh
git add frontend
git commit -m "feat(frontend): implement AI Sana platform UI"
git push -u origin frontend
```

Если менялись общие файлы, просмотрите их diff и добавьте явно. Не включайте в коммит
`.env`, `node_modules`, локальную БД, `.venv` или результаты сборки.
Слияние с `main` выполняется отдельно после проверки командой.

```text
получен через ai-sana-backend.bundle.

Если ветки frontend ещё нет, создай её от доступной backend-ветки с --no-track.
Если frontend уже существует, продолжи её, сохрани текущие изменения и интегрируй
актуальный backend без сброса истории и без force push. При работе из bundle
или с архивированным GitHub-репозиторием продолжай разработку и коммиты локально.

Прочитай backend/docs/frontend-handoff.md, backend/docs/api.md,
backend/docs/architecture.md и backend/README.md. Следуй инструкции передачи задачи.
Реализуй frontend на React + TypeScript + Vite в frontend/ с интерфейсом на русском,
подключённым к настоящему API. Нужны кабинет бизнеса, конструктор с AI-вопросами,
редактирование/подтверждение/публикация, прозрачный рейтинг, общий каталог,
профиль команды, отклики, ручное решение бизнеса и подтверждение этапов.

Используй VITE_API_BASE_URL, демо-пользователей из API и заголовок X-Actor-ID.

не блокируй отклики при низком рейтинге и не выбирай команды автоматически.

на доступный для записи GitHub-репозиторий, выполни git push -u origin frontend.
Если push недоступен, сохрани локальный коммит и сообщи причину. Не объединяй ветку
с main. В конце сообщи хеш коммита, результаты проверок и оставшиеся ограничения.
```
